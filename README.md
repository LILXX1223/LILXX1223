# ICU 护士排班管理系统

基于现有 Django / DRF / SimpleUI、Vue 3 / Vite / Element Plus、SQLite 和 OR-Tools 的本地护理管理研究原型。人员排班和床位分配各自保存、相互关联：先发布排班，再读取正式当班人员进行分床。护士能力、独立资格及人工审核不由模型自动推断。

## 本地启动

在项目根目录运行：

```bash
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

另开终端：

```bash
export PATH="$PWD/.tools/node/bin:$PATH"
cd frontend
npm run dev -- --host 127.0.0.1
```

也可在项目根目录运行 `python scripts/start_dev.py` 启动本地服务；运行日志及 PID 文件在已忽略的 `runtime/`。脚本发现端口已被占用时保留已有进程，不会擅自终止；应自行确认该端口上的服务。

- 业务前台：<http://127.0.0.1:5173/>
- SimpleUI 后台：<http://127.0.0.1:8000/admin/>
- 前端请通过 Vite 地址访问，不要直接打开 `frontend/index.html`。
- Django 使用简体中文、Asia/Shanghai；不要混用 localhost 与 127.0.0.1，以免会话及 CSRF Cookie 不一致。
- 上述是开发服务；生产托管、HTTPS、代理、静态文件和访问控制需单独部署。

当前演示账号 `group3` 为第3组管理账号，`head_nurse` 为护士长只读账号。首次执行演示初始化时默认密码为 `DemoICU!2026`，已有账号的密码不会被初始化脚本重置；原有超级管理员账号保留。原护士个人账号已停用，用户和历史审计记录保留；调班申请由管理账号代录、记录双方确认并审核。开发演示账号不得直接用于正式环境。

## 安装、数据库与备份

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/backup_database.py
python manage.py migrate --plan
python manage.py migrate

export PATH="$PWD/.tools/node/bin:$PATH"
cd frontend
npm ci --legacy-peer-deps
```

数据库引擎固定 SQLite，业务库为根目录 `db.sqlite3`。结构通过 Django 模型和 migrations 维护；禁止重置业务库、删除历史迁移或通过 Navicat 修改业务结构来代替迁移。新安装的演示环境可按需执行 `python manage.py seed_demo`；已有第3组人员时命令不会清空或覆盖现有档案。

`python scripts/backup_database.py` 使用 SQLite 在线备份 API，创建不覆盖已有文件的快照，并在临时目录恢复、执行 `integrity_check` 和逐表计数。**数据库备份不包含头像文件或 AI 主密钥**：还须按授权与保密要求分别备份 `private_uploads/avatars/` 和后端 AI 加密主密钥，并验证完整恢复。不能将数据库、头像、密钥、真实病例或导出文件提交到 Git。

Navicat 是数据库可视化客户端，不是数据库引擎。推荐连接备份副本并只读核对；本机标准应用目录未发现 Navicat，GUI 实际连接和核对尚待在已安装的环境完成。步骤和SQL见 [运维与验收说明](docs/运维与验收.md)。

## 人员与技能

人员信息页面使用同一护士档案，支持搜索、组合筛选、详情、新增和编辑。支持待分组、带教与协作能力、病情评估能力能级；能级按原始资料记录，未定义时不做高低推断。新建护士可不分组，但未分组的固定轮转护士会产生排班阻断提示。

头像支持 JPG/JPEG、PNG、WebP（不超过5MB），可预览、裁剪、替换和移除。后端校验图片并重编码，以受权限保护的接口读取。先保存档案，再保存头像；如头像上传失败会明确提示，已保存的护士档案不会回滚成不存在。

“专科技能覆盖率 → 管理技能”由第3组管理账号直接使用。技能按大组隔离，支持新增、编辑、启用、停用和真实删除，并动态查看关联人数及护士名单。技能稳定 ID 与护士关联、掌握程度、独立资格及有效期分开保存；停用、删除技能不会让床位匹配从旧数据绕过资格约束。删除技能前保存关联和资格快照；较早历史版本未保存过的资格不能事后伪造。

删除护士会在事务中保存档案及技能资格快照，实际删除当前护士行及当前技能关联，清理草稿中的当前责任；正式排班、床位发布、历史申请及工作量事实保留。历史申请在涉及已删除人员时保留原审核事实并标记失效。已删除人员不再作为当前护士参与排班，工作量页面可单独查看其有发布记录的历史。

人员档案可记录特殊排班限制。当前限制是自由文本，排班校验会提示负责人逐项核对；系统不会把自由文字自动解释为已经验证的硬约束。

## AI辅助小组分配

人员页面可配置参与范围、小组数、每组人数、带组资格、带教人员、人员锁定和生效日期。已启用真实 AI 后，系统将必要人员能力资料去姓名化后提交模型，解析并校验返回结构；模型候选仅作为 OR-Tools 的软偏好。实际人数、带组资格、锁定和参与范围由后端单独执行硬校验，负责人可比较三种候选、交换或调整人员，复核后确认。不能因选择了方案就改变已发布历史排班。

方案中的层级分布、年资、技能覆盖、带教支持和稳定性指标均有界面可查看的计算说明，仅作组合比较，不是个人临床能力评分。低年资界限可调整，默认3年只是演示参数，须由科室确认。病情评估能力能级没有明确科室定义时不做高低排序。带组资格和最终指定的带组老师分别记录；AI生成的文字可能有误，须人工核对。

当前只支持当天生效；未来生效的分组版本尚未实现。无真实 API Key 时页面不生成 AI 分组方案；真实人员外发还需医院实际授权和对应服务端开关。真实模型输出仍须人工核对。

分组支持锁定人员、指定同组和避免同组。五项软偏好采用0.0～1.0、步长0.1；OR-Tools 先将每项目标按其计算上界归一化到0～10000，再乘以权重×10形成整数目标系数，硬约束不受权重影响。无有效正式历史小组时，原有分组保留程度不参与优化。人工确认后的分组产生不可变版本；撤销可清空当前归属或在历史方案仍满足当前约束时恢复上一版本，历史快照不足以验证时禁止自动恢复。

分组与床位分配使用相互隔离的后台任务和事件，按真实执行阶段保存数据检查、模型调用、求解状态、评价与候选结果。任务可在页面关闭后查看，进程重启后不会自动继续执行；连续三分钟没有进展的任务在下次查询时标记中断，允许重新提交。当前采用轮询和普通模型响应，不流式展示逐字内容，也不伪造求解器中间解。历史候选不会自动成为正式分组或正式床位责任。

两个业务分别保存对话、经管理人员审核的经验和人工反馈。可执行的长期或仅本次偏好会映射到各自的软目标；暂停后不参与新任务，已有正式版本不变。经验的变更快照由不可变操作日志保存，确认后可恢复有完整快照的历史版本，恢复会创建新修订；此前未保存完整快照的旧版本不能臆造。带组老师变更与床位人工调整均记录必要的上下文，患者病历原文不写入反馈。AI分析反馈只发送已采纳且属于预设类别的原因频次，不发送原始病历。系统尚未自动证明经验的实际改善效果。

## Excel 导入

人员页面“Excel智能导入”支持 `.xlsx` 和 `.xls`，经过上传、字段映射、档案匹配、人工核对和确认五步。系统限制文件、表格和单元格大小；每次保存有修订号。

- 明确字段先用本地规则映射。未配置真实 AI 时不调用模型，也不伪装成 AI 结果。
- 工号可靠匹配现有护士；同名只显示候选，不会仅凭姓名自动覆盖。
- 每条选择新增、更新、跳过或继续核对。空缺字段不会清空旧档案。
- 未知技能需先人工确认并维护技能目录。独立资质必须人工填写有效期并单独确认，普通技能识别不会自动授予资格。
- 缺工号的新合成护士只有在明确勾选时才生成 DEMO 演示编号；真实工号不会被覆盖。
- 确认导入前须处理待核对行和异常；批量操作在事务中执行，错误按行反馈并保留导入记录。
- 可选择通过真实 AI 辅助表头映射；生成的建议须人工应用和复核。真实人员资料外发须获得医院授权，配置开关不能替代正式审批。

## 排班、床位和统计

排班视图有四个选项卡和五个主要操作。固定轮转为 A → N → 夜下休 → 休，长期白班独立配置。草稿支持人工编辑，后端检查资格、人数、跨周休息、夜班衔接及已批准申请；阻断异常未解决不能发布。正式排班保留不可变快照。

智能生成默认按周一开始生成7天，也可选择同一周期的连续14天；轮转始终按原有基准日和小组相位计算，不在第二周重置。草稿和发布版本保存周期长度、班次明细及申请依赖快照；总览仍按自然周汇总，分床按指定日期和班次读取有效正式排班。当前生成器基于既有轮转规则逐日生成，资格、人力和休息要求由发布前校验检查；它不是全周期 OR-Tools 排班求解器，存在阻断问题时必须人工处理并重新校验。

调班申请由授权管理账号代录或编辑。待审核申请直接修订并记录前后内容；修改已批准申请会新建待审核修订，原批准在修订批准前继续有效，修订被驳回时原批准仍保留。撤销保存原因、操作人和时间，不删除申请及审核历史，也不会自动更改正式排班。周期内申请变化会使相关草稿需要重新生成和校验，正式记录的调整须通过已有更正、撤销或重新发布流程处理。

排班表旁的“撤销时段排班”先按日期、人员及班次预览，再通过二次确认执行；正式快照保留，当前有效班次通过撤销记录排除，草稿中的选中排班格被清空。明确重新生成草稿时，会按当前规则重新生成整个所选周期，旧撤销记录不会遮蔽新草稿；原调班申请和历史床位责任记录保留。撤销影响当班护士时，应重新同步并核对床位责任。页头时钟使用服务端初始时间校准并按北京时间显示到秒。

分床同步正式排班及有效护士资格。AI病历识别区分确定/疑似诊断和当前/既往治疗，必须人工核对后才能写入；不得猜测床号。OR-Tools 推荐遵守人数、资格、负荷和三床组合约束，无合规方案时返回错误。人工调整、校验和最终发布均由负责人确认，左右栏读取同一责任关系。新发布版本保留当时患者资料与护士技能快照。

工作量只统计最终发布的排班和床位责任，未连接考勤。N班归属开始日；有效工时来自发布时班次快照。主页面只有总上班人次和累计管床患者人次，个人工时环图位于详情抽屉。已删除人员历史事实在独立区域可追溯。

## 统一 AI 服务配置

系统设置中的“AI服务配置”可由系统管理员填写服务商、HTTPS API 地址、模型和 API Key；默认提供 DeepSeek，也支持其他 OpenAI 兼容接口。Key 初始为空，不在前端源码或本地浏览器存储中保存，读取接口只返回是否配置，不回传原文；第3组管理账号和护士长只能查看状态。

“测试连接”会实际向当前填写的服务发送不含患者或护士资料的请求，不会保存配置；只有收到有效服务响应才显示成功。“保存配置”和“更换密钥”由后端执行；配置保存并不代表连接已测试。未配置时显示“AI服务未配置”，不能将模拟识别冒充真实模型成功。单元测试中的模拟 HTTP 响应仅用于验证程序，不代表真实服务联通。

“AI业务场景配置”按单床、批量、图片预留、护士分组、床位分配、助手聊天、经验分析和 Excel 表头分别保存模型、思考模式、输出 Token 与超时。系统管理员可逐项保存和使用合成数据测试；分组/分床异步任务在创建时保留参数快照。结构化任务固定非流式 JSON，聊天可配置流式文本。图片识别目前仅预留配置，床位页面尚无图片输入；场景测试只证明本次模型请求及格式校验成功，不代表完整临床功能已经验证。

批量病历按明确床号拆分为独立请求。重复床号只有在各段明确写明相同住院号时才会合并，否则要求人工核对；同一住院号出现在不同床位也要求核对。失败床位可单独重试，已成功的结果可独立核对，人工确认前不会写入患者资料。请求编号、模型参数、错误类型、HTTP 状态及用量写入诊断记录，病历原文与密钥不写入该记录。病历输入界面当前仅用于合成病例；不得将真实患者资料标记为合成资料。

API Key 使用 Fernet 加密后存储在 SQLite。加密主密钥由 `ICU_AI_ENCRYPTION_KEY` 环境变量提供，或由后端保存在当前用户 `~/.local/share/icu-scheduler/ai-master.key`（权限0600）中。应将主密钥单独安全保管和备份；主密钥丢失后无法解密既有 API Key，需重新配置。生产环境应使用受控密钥管理和网络出口策略。后端仅允许 HTTPS 公网单播地址、不跟随重定向，并将已校验的 IP 固定到实际连接，同时使用原域名验证 TLS。系统 DNS 将 DeepSeek 官方域名解析为 `198.18.0.0/15` Fake-IP 时，后端通过阿里公共 DNS 的 HTTPS 接口查询该固定域名的公网地址；只发送域名，不发送 API Key、护士或患者信息。其他内网或保留地址仍被拒绝。DNS 检查不能代替生产出口控制。

`.env.example` 列出医院授权开关；患者资料和人员资料外发分别需要 `AI_HOSPITAL_AUTHORIZED` 和 `AI_PERSONNEL_EXTERNAL_AUTHORIZED` 的服务器端授权及医院实际审批。默认不允许真实资料外发。现有基础脱敏不是经过验证的完整去标识化系统，开发和接口测试只使用合成资料。测试专用 `ICU_AI_ALLOW_MOCK=true` 仅用于隔离环境，并须显著标识模拟，不是服务连接成功。

## 智能分配建议、经验与病情评估能力

分组和分床共用建议与经验服务，但按业务类型和授权大组隔离。AI 分析或对话可以生成待审核建议；只有管理人员明确选择本次采用或长期采用后，才会在符合适用条件时转换为该业务的优化参数。无法转换或不适用的内容只作为分析参考，不标记为已纳入求解。当前任务明确设置的软性参数优先于长期偏好；硬性资格、安全规则和当前人工约束始终优先。每轮任务启动时保存经验版本、实际参数和数据快照，新的确认会创建新一轮，旧任务迟到结果不能覆盖新结果。阶段记录区分经验读取、校验、参数转换和真实求解；候选方案对比使用同一口径的业务指标，不比较不同权重下的目标函数总分，也不把方案变化直接归因于某条经验。

护士的病情评估能级取自人员档案，1 级表示较高能力，缺失值不从护理层级、年资或专科技能推断。分组可将已记录能级的合理分布作为软性目标。床位匹配另设患者“病情评估需求”，需经人工确认；不能以护理负荷或未经核对的 AI 病历结果代替。只有患者需求确认较高且该患者所有符合既有硬性资格的候选护士均有有效能级时，病情评估能力匹配才作为软性目标加入该患者的求解；资料不足时保留既有硬性规则并提示待核对。分组和分床的候选结果都须由管理人员审核确认；该能力维度及人数配置不构成经验证的临床安全评分。

## 检查与测试

在项目根目录：

```bash
source .venv/bin/activate
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
python -m pip check
python scripts/check_sqlite_concurrency.py
python scripts/run_browser_tests.py
python scripts/run_browser_tests.py --real-ai  # 可选：真实模型，仅隔离合成数据
python scripts/run_browser_tests.py --real-ai e2e/real-ai-experience.spec.js  # 可选：真实反馈经验联调
python scripts/run_browser_tests.py --real-ai e2e/real-ai-medical.spec.js  # 可选：真实模型的合成单床与长文本批量识别
python scripts/run_browser_tests.py --real-ai e2e/real-ai-scenes.spec.js  # 可选：真实模型四种思考模式和流式测试
export PATH="$PWD/.tools/node/bin:$PATH"
cd frontend
npm run build
```

浏览器测试脚本自动创建临时 SQLite 数据库、合成演示数据和独立前后端服务，测试结束后清理。普通测试不连接当前业务数据库；`--real-ai` 只从业务库只读复制加密后的 AI 配置到临时库，不读取业务人员或患者，也不向业务库写入。测试会创建、修改和删除合成资料，必须使用此隔离脚本，不能将浏览器测试指向正在使用的业务库。临时管理员密码由脚本生成，不写入项目代码。

上述测试与备份检查不能替代医院上线评估。真实服务的可用性会随配置和网络变化；临床阈值签署、隐私与安全评估、生产并发压力测试、HIS/EMR/考勤接入和完整灾难恢复仍需在目标环境开展；不应将本项目声称为已经具备临床上线条件。
# 批量病历识别：逐床任务与恢复

床位分配中的批量识别先按明确床号拆分，并用稳定床位 ID 校验当前大组；未选择合成空床导入时跳过空床。同组同一时刻最多处理一个病例。各病例调用与单床相同的 Django 识别服务，成功后立即保存为待人工核对的 `Extraction`，不会自动创建或覆盖患者。失败可逐床重试；权限或共享 AI 身份验证失败会暂停后续处理。患者状态在模型调用期间变化时，结果不会直接保存。

新批次默认勾选“本批采用系统设置中的单床识别参数”，可取消后使用系统设置中的批量场景；所选模型、思考模式、Token 和超时随任务保存，原有模型、API 地址、密钥及场景设置均不被改写。具体参数以界面及任务快照为准。实时显示的进度来自各病例数据库状态，不代表已完成患者导入。

本实现使用浏览器受控队列而不是后台常驻工作进程：关闭页面后未启动的病例暂停，重新打开床位分配页面会恢复最后一次任务及待核对结果。短期暂存的原始病历使用后端密钥加密，成功后立即清除；加密文本超过两小时不能继续解密，打开任务时会清除已过期暂存。长期无人访问时，部署管理员应安排定期执行 `python manage.py purge_medical_batch_staging` 清理过期密文；该命令不删除已保存的识别结果。数据库备份及 SQLite WAL 的保留和清理仍须遵循院方的数据管理要求。
